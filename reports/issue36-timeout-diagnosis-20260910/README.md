# 独立评审 120 秒超时诊断

2026-09-10，应用户要求检查第二次请求。确定存在的问题是：独立评审入口把等待时间
写死为 120 秒，使用非流式响应；错误归档又丢失了异常来源和请求阶段。
这不是查证得到的 Ark 或 GLM-5.3 服务端固定时限。

## 原始事实与判断边界

原始执行代码为 `e32ad7c8b009a69836f141690c4731536d79eac6`。第二次请求于
`2026-09-10T03:16:48.347676+00:00` 开始，在
`2026-09-10T03:18:48.415961+00:00` 结束，记录耗时 120.066 秒、一次尝试和
`failure_type=timeout`。原始记录见[进度文件](../issue36-node-reviews-20260910/output/model-progress.ndjson)。

| 已核对事实 | 能支持的判断 |
|---|---|
| 冻结计划 `timeout_seconds=120`，传给 `urlopen` | 120 秒来源于本地客户端配置 |
| 首次成功耗时 84.829 秒，输出 3256 token，其中推理 2791 token | 非流式思考请求有较长等待，120 秒余量不足；不能据此预测第二次实际耗时 |
| 第二次输出材料仅 300 字符，另有 450 字符上游；与首次同为 8 份来源 | 没有材料体积暴增的证据，但生成时间不由输入长度单独决定 |
| 旧代码将本地 `TimeoutError` 和 HTTP 408 都映射为 `timeout` | 历史记录无法区分本地等待耗尽与服务端返回 408 |
| 旧错误记录没有 HTTP 状态、响应头等待时间或供应商请求 ID | 无法追溯它在连接、等待响应头还是读取响应体阶段失败 |

120.066 秒与配置值高度吻合，**客户端等待耗尽是最有力的解释，但并未被旧日志唯一证明**。
不能将其写成已确认的供应商故障、限流、模型生成卡死或代理故障。
`urllib` 的该参数控制阻塞 socket 操作，不能宣称是整个请求的严格总墙钟截止时间。

## 官方默认值

核对火山引擎官方 Python SDK 固定提交
[`bd7d94433803d213a85f918ff2eb049067655eff` 的超时常量](https://github.com/volcengine/volcengine-python-sdk/blob/bd7d94433803d213a85f918ff2eb049067655eff/volcenginesdkarkruntime/_constants.py)：
默认请求等待为 600 秒、连接等待为 60 秒。它提供设置等待余量的参考，
不是 GLM-5.3 的响应 SLA；本项目仍使用 urllib，未复制 SDK 的重试设置或宣称超时语义完全一致。

无模型调用的连通性检查只能说明检查时端点可达，不能还原失败时的连接状态，
也不能验证认证、额度或生成服务。本报告不发布本机网络环境配置。

## 修复与验证

- 独立评审新增 `--timeout-seconds`，默认 600 秒，接受大于 0 且至多 600 的有限数值。
  参数写入 `k3-independent-review-v2` 计划，付费入口继续核对材料、代码和整个预检；
  改变等待值后旧批准预检不再匹配。其他实验及应用入口的默认值不受此修改影响。
- 传输层保留 `failure_origin`、`phase`、异常类型及已收到的 HTTP 状态、供应商请求 ID、
  响应头等待时间。`connect-or-response-headers` 如实表示 urllib 无法进一步区分的阶段。
  不记录认证头、Cookie、原始异常文本或完整请求。评审错误产物保留诊断与耗时。
- 零重试、首错停止、未知用量保持未知的规则不变。本次没有新增供应商模型调用。

确定性测试覆盖本地超时、包装在 `URLError` 内的超时、连接错误、响应体超时、
HTTP 408、408 响应体读取超时、响应解析失败、成功用量以及冻结参数变更阻断。
`uv run pytest` 完整通过 **582 项**，耗时 52.67 秒，包含 TypeScript 宿主契约测试。
原始评审审计脚本再次通过，核验 5 个输出索引文件和 12 个原始材料文件；
仍为两次调用、一份有效评分、已知 2.2194 AFP、完整费用未知。

[本机复现脚本](reproduce.py)只监听 `127.0.0.1`，显式绕过代理，不使用模型凭据。
[实测结果](local-reproduction.json)显示：服务延迟 200 毫秒返回响应头时，50 毫秒等待
在 52 毫秒失败；同样服务改为 1 秒等待后，在 201 毫秒收到 HTTP 200。
响应体延迟被记录为 `response-body`，即时 HTTP 408 保留状态。
这证明修复的等待配置和诊断机制有效，不等于复现了当时供应商内部的状态。
