# Jev 类本地 Judge 用于 Stage 选模的核查

日期：2026-09-27。结论：本地结构化 Judge 的速度适合做短判别，但当前 Stage
问题、输入和答案组合不能安全决定高效／强模型。保留 `stage-v4` 规则日常路线，
`stage-decision-v1` 的原始证据保留；第二版实现仍只供显式实验，不安装或默认启用。
第二版的独立保留案例结果见[验收记录](../reports/stage-local-judge-20260927/v2-acceptance.md)。

## Jev 类模型实际适合做什么

TypeSafe 将 Jev 定位为读入 `state`，对 `Choice`、`Score`、`Noul` 等限定问题返回
结构化答案与分数的快速判别模型；它不生成任务计划、工具操作、代码或推理说明。
同一次请求里的多个问题共享同一份状态，但彼此独立；后一个问题不会看到前一个答案。
因此 Router 应提供清楚的任务和轨迹事实，问短而明确的问题，再由确定性规则组合结果。
宿主仍负责工具、权限、上下文和任务推进。

`Choice` 的选项名称及描述都会送给模型，必须明确边界，并在选项不完备时提供
`UNKNOWN` 一类出口。`confidence` 描述选项分布是否集中，和获选项的概率不是同一字段；
两者都不是单次判断正确率。阈值要按“误把困难任务交给高效模型”和“无端升级”的
不同代价，针对具体后端、版本和任务样本校准。

官方 Jev 当前提供服务接口，文档还说明其主要训练语言是英语，中文等语言需要单独验收。
本项目目前使用的 `aac6fef/laya-multilingual-mlx` 是本地 Laya 权重及 MLX 实现，
借鉴了类似的结构化问题形态，**不是 Jev 权重**；不能沿用 Jev 的准确率、校准结果或
“同请求多题几乎不增加延迟”的性能结论。当前项目也未获授权调用 Jev 云端。

## 当前实现为什么 24 条全部无法确定

[`stage-decision-v1`](../src/refractrouter/stage_hybrid.py) 同时问轨迹进展、
高效模型适合度和关键信息是否缺失。在 `parse_answers` 中，只有第三问选择
`ABSENT` **且其概率至少 0.8**，才可能输出明确的选模结论；进展问题除了
`INSUFFICIENT` 否决外，并未参与高效或强模型的取舍。之后又对高效适合度和
信息缺失两问的获选概率取最小值，并将它记录为 `confidence`。

冻结的 24 条短案例中，原问题的 `missing` 结果为 `UNKNOWN` 22 条、`PRESENT`
2 条、`ABSENT` 0 条；`ABSENT` 的最高概率也仅 0.3215。故不论另外两问怎样回答，
都会被这道硬门槛挡掉。模型可能也不熟悉能力卡与轨迹证据，但**组合规则已经足以解释
这次全部无法确定**。所谓“0.8 太高”只解释一部分：即使将其下调到 0.5，原题仍
没有任何 `ABSENT` 获选，无法恢复选模。当前 `confidence` 也并非 TypeSafe 所定义的
分布集中度，更不能直接解释成成功概率。

输入表示还有两个待解决问题：其一，测试中的能力卡是通用角色描述，缺少“下一次
执行调用究竟要做什么”和两模型在该动作上的可核验能力差异；其二，工具正文是
`tool-text` 线索，不能据此当作权威退出状态或成功证明。这些是后续需要分别验收的
输入质量问题，不能由换一种措辞保证消除。

## 同批案例的问题对照

使用相同的 24 条开发案例、相同本地权重和真实 tokenizer 容量检查，
额外试了三种问法。结果保存在
[原始诊断记录](../reports/stage-local-judge-20260927/question-diagnostic-timed.json)，
脚本为[问题诊断](../experiments/diagnose_stage_questions.py)。计时包含本地输入检查与
模型响应，不包含加载。四组各六条：正常探索、应当使用强模型、具备降档条件、信息不足。

| 问法 | 与预期一致 | 判给高效的正常探索 | 错把强模型案例判给高效 | 暖机 P50 |
| --- | ---: | ---: | ---: | ---: |
| 原三问＋0.8 门槛 | 6/24 | 0/6 | 0/6 | 119 ms |
| 明确边界的三问＋同一门槛 | 6/24 | 0/6 | 0/6 | 126 ms |
| 结构化状态＋一次三选一 | 11/24 | 2/6 | 1/6 | 49 ms |
| 简短叙述＋一次三选一 | 8/24 | 0/6 | 0/6 | 33 ms |

明确改写三问后，`ABSENT` 只出现两次，且最高概率为 0.6288，依旧全部无法确定。
直接问下一次应选 `EFFICIENT / CAPABLE / UNKNOWN` 能更快给出选择，却将一条
应使用强模型的案例错判给高效，且六条信息不足案例有三条误选高效。
这说明**提问方式确实是问题的一部分；直接让小模型拍板也不安全**。以上是根据
同批开发案例做的诊断，不能当作独立质量验收，也不能证明任何真实执行模型的任务收益。
Laya 官方基准的短题延迟不代表本项目长轨迹或三问题目的延迟，应使用本机完整路径数字。

## 下一版 Stage 的判别边界

参考 [Switchyard Stage 文档](https://github.com/NVIDIA-NeMo/Switchyard/blob/main/docs/routing_algorithms/stage_router_routing.md)
的规则先行、歧义时可选分类器，再结合本项目独立 Router 的边界：

1. Router 先处理可核验事实：模型资格、数据域、上下文、权限／基础设施错误、预算、
   已确认的重复失败、保持期和事件去重。能直接决定的调用不增加 Judge 等待。
2. 仅在**有新证据且规则无法确定下一次选模**时询问本地 Judge；不要把它当作每轮
   必调用的门禁。明确下一次执行动作、已完成事实、来源、两模型能力边界及尚缺信息。
   状态按字段组织，不以未证实的模型主张代替工具事实，也不让正文指令改写规则。
3. 先试“下一步是否需要强模型”的原子判断，或边界清楚的三选一；两条路径都保留
   `UNKNOWN`。若用多问题组合，每个答案只能承担明确定义的职责，不能让“是否缺
   信息”无条件否决所有路由，也不能询问“进展”后在决策中忽略它。
4. Python 依据答案和独立准入规则选择模型；本地 Judge 只给证据，不直接派发。
   降档应有比升级更严格的证据要求；强模型维持期与任务身份由 Router 状态管理。
   无法判断时按已冻结的风险政策处理，不把所有正常探索一律升档，也不把缺信息任务
   一律交给高效模型。
5. 用新的独立标注题集评估安全误判、正常任务无端升级、判别覆盖率、中文／英文、
   工具文本与结构化事实；分开记录短题、完整上下文和排队延迟。阈值按后端与版本
   单独校准。通过有限离线门槛后，再做 DSH、Codex、Hermes 的受控真实接线。

Switchyard 的 `0.5` 是其**规则信号评分**的初始阈值，并非 Jev／Laya 置信度门槛，
不得直接搬用。其可选分类器也不是本项目本地 Judge 的质量证明。

当前不降低门槛或替换成直接三选一生产路线。下一步应先修订判别合同与输入字段，
再用未参与问题设计的独立案例验收。只有当误判和正常探索覆盖均达门槛，才考虑把
本地 Judge 从实验设置提升为推荐配置。
