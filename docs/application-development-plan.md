# RefractRouter 团队集中路由应用开发计划

更新：2026-09-08。依据：用户确认的应用开发定位、现有代码与在途实现，
以及本次通过 GitHub CLI 重新读取的 issue 和 PR 状态。
本文件作为后续应用开发的排期依据；上一轮研究审阅的路线和技能相关建议
不再指导当前开发，已完成实验的原始证据继续保留。

## 1. 产品目标与取舍

让团队成员通过统一入口提交任务，选择“省成本／均衡／质量优先”，
由 RefractRouter 管理模型选择和执行，在预算与等待时间限制内交付可用结果。
维护者可以发布统一策略、追踪任务与费用，并根据实际使用情况调整配置。

RefractAgent 是面向使用者的应用入口；RefractRouter 是其 Python 路由核心；
DSH 插件负责把应用接入宿主的模型选择、会话、凭证和进程服务。
先交付本机 DSH 入口，保留后续复用核心接入其他客户端的能力。

当前取舍如下：

- 暂不考虑 WikiSkill、技能生成、技能迁移和知识反馈，不为它们新增接口或排期。
- 以任务可用、操作简单、费用可信、失败可处理作为推进标准。
  文献新颖性、oracle 差距、跨领域统计结论不作为应用发布条件。
- 保留契约校验、预算限制和必要的结果检查。应用定位不降低运行正确性要求。
- 默认直接按已发布策略执行；简单任务整任务处理，适合的高频任务复用计划。
  拆分、并行与混合模型是可选执行能力，不要求每个任务都使用。
- 先完成一个成员的使用流程，再做小范围试用，随后建设集中管理。
  单独维护一份共享配置，只能算配置统一，不能算已有团队级执行控制。

首批场景暂定为给定材料的方案比较、约束核对和结构化分析。
用近期团队任务进一步选定最值得支持的一类。当前文本入口的交付是分析与生成结果；
实际浏览网页、修改文件、运行代码及图片、视频生成留待相应能力接入与验收。

## 2. 实际进度与剩余缺口

截至本次核对，[#32][i32] 已关闭，[PR #35][pr35] 和 [PR #37][pr37] 已合并。
已有 DAG 校验、节点选模、调度、预算账本、有限恢复和 DSH 文本工具，
可以直接作为应用基础。

工作区 `codex/local-strategy-models` 另有未提交的应用实现。
以下区分已合并能力、在途代码和验收状态，避免把“有代码”写成“可发布”：

| 能力 | 当前状态 | 应用交付还缺什么 |
| --- | --- | --- |
| 路由与执行核心 | main 已有执行基础；在途正确性修复及完整回归已通过 | 审阅并合并本机应用改动 |
| 用户策略入口 | 三种原生模型、网页选择、会话传递及真实回答与独立评审均已跑通 | 试用中改进严格格式检查，特别是字数约束 |
| 独立安装 | 最终 wheel、插件 tgz、配置命令和源码外安装验收均通过 | 第二阶段由第二位成员独立安装 |
| 本机运行证据 | 最终回归、安装与网页模拟通过；三种策略共 6 次真实调用完成 | 第二阶段扩大到成员真实工作，保留本次长度漏检问题 |
| 团队共享 | 尚无集中任务服务、全局额度和成员级任务台账 | 小范围试用后交付最小集中管理能力 |

应用开发继续推进后，完整回归已更新为 396 项测试与 5 项子测试通过，
最终安装包的 headless 模拟验收也已通过，并增加用户任务原文检查。
DSH 网页验收发现的消息来源识别问题与原生凭据引用问题已有修复及回归覆盖。
真实验收共完成 6 次调用，生产 1.4509 AFP、评审 5.609 AFP，无重试或未知用量。
三种输出的成本计算与推荐正确；M3 超过严格的 250 字符要求，独立评审漏检，
作为后续格式检查问题保留，不将模型评审分数当作确定性合规保证。
最新证据见 [本机应用验收](../reports/refractagent-local/20260908/README.md)。

## 3. 使用者应得到什么

1. 按文档安装 RefractAgent 核心与 DSH 插件，完成配置检查。
2. 启动本机 DSH，在模型选择器中选择省成本、均衡或质量优先。
3. 输入任务、材料和交付要求；普通任务不需要填写模型权重或编写 DAG JSON。
4. 取得答案，并能看到使用的物理模型、执行状态、耗时、费用和记录位置。
5. 遇到失败、超时或取消时，能理解当前状态并取回已有结果；重复执行前能确认费用。

三种策略表达不同选择偏好。它们在同一任务上可能选到相同模型，
“质量优先”也不保证每次得到最高质量。验收要核对实际选择符合配置，
同时判断最终结果能否使用，不能为了展示差异强制选三个不同模型。

模型目录继续保留已登记的 GLM、Kimi 和 Doubao 等条目；目录登记、接口接通、
场景验收通过、进入默认候选池分别管理。第一阶段只启用少量已适配的文本模型。
图片、视频等接口需要独立的任务类型、产物处理和计费适配，不与文本调用混为一项。

## 4. 第一阶段：交付可安装、可使用的本机版本

**阶段成果：成员安装核心和插件后，可以在本机 DSH 中选择三种包装模型接口，
完成真实文本任务并查看运行记录。**

| 顺序 | 工作包 | 验收条件 |
| --- | --- | --- |
| 1 | 收口运行正确性 | 合法的整体失败能保留；非空输出的异常零用量不能形成免费候选；恢复不违反剩余预算与启动时序；相关回归通过 |
| 2 | 完成三种策略接口 | Python 管理预设与选模，DSH 注册三个可选择模型；任务和会话上下文完整传入，正常使用无需逐节点配置 |
| 3 | 完成结果与失败处理 | 答案、执行状态、质量状态分开；生成成功而评审失败时保留答案；费用未知、超时和取消有明确记录 |
| 4 | 固定安装交付 | 核心与插件版本匹配；脱离源码目录也能运行；配置不依赖开发者路径；安装、升级及常见故障说明齐全 |
| 5 | 完成本机验收 | 最终版本的完整测试、类型检查、构建通过；安装包模拟验证通过；DSH 模型选择与三种策略真实任务验证通过 |

默认先提供整任务处理与少量可复用计划；自动规划和局部恢复保持显式选择，
不在普通请求中探测所有模型，也不因一次失败自动扩大调用范围。

第一阶段验收分三层记录：

- **机制检查**：确定性测试覆盖选路、预算、用量、取消、错误和进程边界，不发起付费调用。
- **安装与宿主检查**：使用最终 wheel 和 tgz，在源码目录外安装，
  检查 DSH 可发现、可选择三个模型，并完成模拟会话。模型目录测试不能代替实际选择检查。
- **真实任务检查**：使用同一组明确交付要求的文本任务运行三种策略，
  检查答案、模型、时延、生产与评审费用。模拟回答不计入这一层。

真实调用依照仓库已有规则核对有效的范围与预算授权，使用新的输出目录及
Ark Agent Plan `/api/plan/v3`，保留全部尝试的费用。准备安装包、预检和文档不需要先付费。

本阶段按照用户明确的本机安装、选择模型接口和真实任务跑通标准验收。
第二位成员独立安装属于下一阶段的可用性验证；自动安装检查与成员试用分别记录。

## 5. 第二阶段：用真实工作确认应用价值

**阶段成果：明确哪些任务值得继续支持，修复最影响使用的具体问题。**

先请第二位成员按文档独立安装并完成一次任务，再邀请 2–3 位成员，
收集约 10–20 个近期任务，优先覆盖同一高频场景。
这些数量用于控制试用规模，不承担统计泛化结论。
短期内可以使用本机版本和简单反馈表，不以完整管理后台作为试用前提。

| 关注项 | 记录 | 下一步决策 |
| --- | --- | --- |
| 结果可用性 | 可直接使用／需要修改／不可用，附原因 | 修复最常见失败，明确支持范围 |
| 使用负担 | 安装问题、提交步骤、人工介入及修改时间 | 简化入口与默认配置 |
| 实际代价 | 全部尝试的生产费用、必要评审、规划或外层开销、真实等待时间 | 调整策略和输出上限，决定是否拆分 |
| 策略是否有意义 | 成员为何选择某策略，结果是否符合预期 | 改善策略命名、默认值和解释 |

只对影响产品决策的任务，与成员原来直接调用固定模型的方式做小规模比较。
如果整任务单模型更适合该场景，就将其作为默认路径；不为维持 DAG 形式增加操作和费用。
开发期的独立评审用于验收，正常使用是否每次评审按场景明确配置；未评审不能显示质量通过。

进入团队集中使用前，首批必过任务已通过，阻断交付或损坏账本的问题已处理，
成员的使用记录和下一轮优先问题清单齐全。

## 6. 第三阶段：建设最小团队集中管理

**阶段成果：成员使用同一套已发布规则，任务与费用可以按成员和项目管理。**

根据试用明确的需求，先采用单一受管理的 Python 执行服务和共享任务存储，
让 DSH 作为客户端接入；初期可使用一台团队管理的机器承载。
服务协议与存储选择在实现前形成简短设计，保留现有 Python／TypeScript 职责边界。

必须交付的能力：

- 模型和策略配置版本化发布、回滚；进行中的任务使用提交时的版本。
- 成员身份、项目归属与任务访问控制，成员可查询自己的历史任务，维护者查看必要汇总。
- 持久化任务状态、结果位置与费用账本；重启后能识别未完成和费用未确认的调用。
- 共享派发入口的跨任务并发、额度预留和结算；超时或重启不能把已发出的调用当作免费。
- 请求幂等，避免重复点击或网络重发造成重复付费；取消停止后续派发。

验收覆盖两个成员同时提交、重复提交、额度不足、取消、服务重启、配置回滚和越权读取。
初期不引入多区域部署、分布式调度或复杂运营后台。
如果之后要求模型在每位成员本机执行，需要另行设计集中额度预留，
仅收集本地运行记录不足以强制实施团队全局预算。

## 7. 第四阶段：按使用问题扩展能力

由前两轮使用结果决定顺序，每次扩展都需要一个具体任务和对应验收：

- 某类任务质量不足：调整提示、计划或启用经验证的新模型。
- 某类任务等待过长：确认可并行部分，再优化调度。
- 某类失败频繁且可恢复：启用有界局部恢复，比较交付改善与额外费用。
- 手工计划维护成本高：优先验证自动规划，允许不拆分。
- 团队确实需要工具、图片或视频：扩展能力协议、适配器、产物与计费，再纳入策略选择。

每个对照都应回答“接下来改哪一项配置或能力”。
没有对应产品决策时，暂停大规模模型矩阵、重复 oracle 和跨领域研究实验。

应用总事项按四项成果推进：

1. 本机版本：正确性、三种模型接口、安装与真实任务验收。

## 9. 紧接着的执行顺序

`codex/local-strategy-models` 已完成第一阶段的本机安装、三种接口选择和真实执行，
安装包、完整回归、答案、费用及已知限制均已交付；代码与证据进入应用 PR 审阅，
合并与后续试用在 [#41][i41] 跟踪，严格输出约束在 [#42][i42] 跟踪。

1. 审阅本机应用变更，按确认范围提交与合并。
2. 第二位成员按安装说明独立完成一个实际任务，记录安装与使用问题。
3. 收集同一高频场景的近期任务，按第二阶段开展小范围试用。
4. 优先处理影响可用性的失败；已知的长度约束与评审漏检纳入这一轮。

第一阶段不夹带团队数据库、管理后台或 WikiSkill。
原有研究材料继续用于解释历史问题和辅助排查，日常开发优先级由这份应用计划决定。
