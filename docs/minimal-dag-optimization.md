关联 [Issue #72](https://github.com/AEALab/RefractRouter/issues/72)，承接 #54；

## 使用入口

本阶段提供 Python 核心与已安装 `refractagent` 的实验入口，暂不增加 DSH 设置项。
历史自动模式不变，新策略必须在请求 JSON 中显式启用：

```json
{
  "task": "根据所附材料，逐条核对方案费用和适用条件，保留例外后给出建议。材料：……",
  "template": "auto",
  "plannerPolicy": "minimal-v1",
  "maxConcurrency": 4,
  "acceptanceCriteria": ["覆盖所有费用和条件", "保留例外及来源依据"]
}
```

将完整请求保存为 `request.json`，先执行零调用预检：

```bash
uv run refractagent run --request-file request.json \
  --provider-config provider-config.json --mode preflight --runs-dir /tmp/minimal-dag-preflight
```

预检和模拟展示模板，不调用规划模型，不能验证新策略的实际规划选择。
开发集真实调用须另行冻结代码、模型、任务、重复数、调用上限、停止条件及新输出路径；
使用 `--mode live --execute-paid-run` 才执行真实请求。禁止把预检结果作为收益证据。

## 一次规划选择执行方式

`minimal-v1` 仅适用于 `template: auto` 的紧凑规划；不接受提供计划、完整契约规划或
`maxPlanRepairs: 1` 的组合。规划返回结构错误后如实结算并失败，不增加修复调用。
默认按配置时延和价格选择规划模型，也可显式指定 `plannerModelId`。
模型规模不能从价格推出；快速响应仍需真实验证。

规划器在同一次调用中决定：

| 决策 | 含义与校验 |
| --- | --- |
| `direct` | 合并后只有一个交付节点。自动选择单节点仍计入本次规划调用。 |
| `parallel` | 有结构独立的分支，且候选模型所属 provider 的配置并发容量上限至少为二。 |
| `tool` | 多节点，当前执行环境有可用工具，并说明先取得哪些证据。 |
| `capacity` | 多节点，说明具体容量限制；只是模型声明，实际容量仍由运行时准入校验。 |
| `isolation` | 多节点，说明必须隔离的职责；这是待审查的理由，不是已证明的收益。 |

单节点、分支数及依赖由任务决定，未固定为三个节点。无具体理由时优先单节点；
短小、强耦合工作在规划时直接合并，不生成读题、制订计划或纯复述节点。
串行链的最后节点可以直接交付，分支汇合时只做必要的综合与决策。

结构上的并行机会不是实际并发保证。最终选模、节点准入、provider 派发间隔及实际服务
时延仍影响调度。容量和职责隔离理由也未经过独立语义验证，不能直接称为合理拆分。
本阶段所有节点仍收到全文，因此不支持通过材料分片突破单节点输入容量。

## 显式合并与安全边界

规划器优先直接输出精简后的图，也可选填 `merge_groups`，例如
`[["facts", "answer"]]`，表示这些职责在同一次节点调用内完成。
Python 在任何节点派发前编译这些分组：

- 保留全部职责文本和组内推理依赖，保留外部依赖及下游字段交接。
- 保留最终交付节点 ID 和验收覆盖，合并后的难度、风险取组内较高值。
- 拒绝未知节点、重复或重叠分组，以及合并后产生的环路；不删除依赖来修复图。
- 不扫描或改写正在运行的图，不重放工具，也不凭名称推断两个节点语义等价。

合并后的请求继续经过既有容量、预算、模型准入、依赖事实检查与交付评审。
`job` 和 `reason` 的短描述限制仅作用于规划 JSON，未给最终答案增加字数限制，
也未恢复规划的隐藏超时或输出上限。

`minimal-v1` 默认关闭运行中再拆，以便隔离首次规划的作用。若显式设置
`maxDynamicSplits`，仍使用原有的有界动态策略，并单独记账；不能把该路线当作
无恢复对照。取消、在途结算、工具次数及费用限制继续遵循既有运行时。

## 证据与后续顺序

`result.json` 的 `compact_planning` 保存策略版本、模型原始输出、解析错误、规划耗时
以及有效决策。`summary.json` 暴露 `planning_policy` 与 `planning_decision`。
决策记录包括提议节点数、合并后的节点数、合并分组和配置并发容量上限。
`semantic_necessity_verified` 与 `benefit_verified` 均为 `false`，避免将结构检查当成研究结论。
规划、节点执行及最终评审继续进入原账本；显式 `single` 模式仍跳过规划调用。

第一阶段的回归验证是无网络工程验证，尚未证明模型实际会更合理地拆分、成果质量不降，
或真实耗时与 AFP 改善。后续按 #72 顺序推进材料/中间交接精简，再验证稳定前缀与缓存。
最终交付评审保持不变；正式独立留出实验仍需 #52 的真人门槛。
