工具续接、上下文压缩及同一轮追加指导沿用这个选择，不建立 DAG，也不在工具循环中重复判别。

## Task 选模

Task 的执行模型来自有序模型池。Python 根据本次输入实际需要的媒体能力，先排除不能主持
Agent、未接通图片输入或未接通影片输入的候选。只有一个候选时直接选用；多个候选时才调用
配置的 Judge。达到初始适合度门槛后，同计费单位先比较首次执行调用费用上界；
上界相同且缺少可比时延数据时按用户设置的池顺序选择。

当前共同判别合同为 `task-decision-v2`，要求逐候选提供适合度与信息不足信号。
旧 `task-decision-v1` 的 `choice`、`score`、`noul` 结果仅保留历史解释用途。任务正文属于
待判断数据，不能修改候选集合、规则或门槛。路由只接受配置中存在的候选 ID；非法结构、伪造 ID
和无法核对的分数都会停止任务，不会自动追加一次“修复 Judge”调用。

不确定、输入超过 Judge 容量或关键信息不足时，只检查用户指定的备援模型。备援不满足媒体能力、
数据域或预算时直接停止，不轮流尝试其他模型。

## 两类 Judge

### 轻量 LLM Judge

LLM Judge 独立于执行模型池，从 DSH 模型目录选择。每个任务至多调用一次，关闭工具，要求结构化
结果。推理等级读取该 Judge 模型在 DSH 中真实支持的选项。

## 图片接入与持久化

DSH 模型目录声明图片输入，且本项目适配达到 `connected` 或 `verified` 时，规划路由虚拟模型才向
宿主声明 `image` 输入。图片内容块和附件引用原样进入底层模型；Python Judge 只读取文字和图片
元数据，不读取或上传二进制内容。

`refract_generate_image` 是受管原生工具。它按以下顺序执行：

1. Python 核对 Task 身份、媒体路线、数据域和预算并原子预留。
2. TypeScript 从 DSH 凭证服务取得引用，对 Ark Agent Plan 图片接口进行一次提交。
3. 结果只从允许的 HTTPS 产物域下载，并保存为 DSH 图片附件。
4. Python 按实际图片张数结算，轨迹保存模型、操作、附件引用与费用。

凭证或参考图片在 HTTP 派发前失败会释放预留。提交结果不明、下载失败或附件保存失败会保留
待核对状态并停止后续受管调用，不会再次生成。

媒体路线同时记录 `declared`、`connected` 和 `verified` 层级。设置页可导入经官方资料核对并完成
适配接线的 Seedream 路线，但只有完成真实接口验收、标记为 `verified` 的路线可以派发。这样不会把
官方声明或离线模拟结果冒充实际可用性。

## 影片宿主缺口

当前 DSH 0.1.5 的原生 `ContentBlockMap` 只有文字、推理、图片、工具调用与工具结果；附件服务也
只有 `saveImages` 和 `readImage`。本插件无法在不修改宿主的情况下提供可回放的原生影片输入、
播放器和持久附件。因此本版不会把抽帧标成影片输入，也不会把过期提供方 URL 标成已保存产物。
本机已安装包的类型合同位于 `@deepseek-ai/dsh-llm/lib/types/types.d.ts` 与
`@deepseek-ai/dsh-attachment/lib/types/index.d.ts`；前者的 `ContentBlockMap` 无 `video`，
后者的 `AttachmentStore` 无影片保存、读取方法。后续需在 DSH 宿主源码中完成合同及适配，
再回到本仓库接通受管视频工具与会话展示。

完成 T4 需要 DSH 宿主先提供并验收：

- `VideoAttachmentRef`、影片保存与读取服务；
- `video` 内容块及模型适配器的原生投影；
- 上传、播放、下载、导出与权限处理；
- 上下文压缩、历史 replay 和会话恢复合同；
- 异步生成任务的稳定操作 ID 与已有任务查询入口。

Python 已具备媒体非 token 预留和 `submitted/running/succeeded/failed/cancelled/unknown` 状态合同，
可在宿主能力到位后承接影片任务。当前不得据此宣称影片已接通。

## 计费与安全

LLM、图片和后续影片费用统一进入 Python 账本。AFP 与现金分账；USD 来源保留原币及冻结汇率，
产品界面优先显示 CNY。图片按张数预留和结算；用量不明时保留预留。预算、期限与最大调用数继续
使用 `0` 表示不设置产品上限。

本地 Judge 只解决判别数据的本地处理，不能替代执行模型或媒体路线各自的数据域授权。每条媒体
路线仍需独立的部署域、信任策略、凭证引用、接口和可核对价格。

无网络测试覆盖多候选、单候选、无候选、不确定、伪造 ID、媒体能力筛选、LLM 与本地 Judge、
非 token 预算、提交结果不明、派发前取消、图片附件保存和旧 replay 读取。

真实功能验收仍需新的付费范围授权，并冻结确切模型、输出规格、调用次数及 AFP/CNY 上限。
未执行真实调用前，Seedream 保持 `connected`；影片保持未接通。测试、构建或能力标签不能替代
真实接口验收。

当前模型池两条路线的已知文本和工具能力近似；火山方舟资料不能证明哪条在具体
代码或研究任务上更强。因此，即使改进本地 Judge 的提问方式，仍需要冻结真实
任务和独立结果评价，才有依据让它在两条路线之间做质量选择。本阶段以零云端调用
完成接口审计、能力资料和本地复现；真实正常自选路线未满足判别质量门槛，不把
新的付费调用当作选模质量的替代证据。

### 2026-09-26 判据修订与直选实验

上节的 2／6、4／8 等数字是按原始单一答案标签计算的，**不能当作产品选模质量**。
其中八道模拟「某候选有工具或媒体能力」的题目，应由 Python 结构化资格检查处理；
部分逐工具能力尚未进入准入合同，更不能让 Judge 的回答代替验收。四道指代不清题
要求安全备用；两道已知能力相同的普通文字题允许任一合格候选，备用也属安全结果，
但应另计正常自选覆盖率。修订标签在
`data/task-judge-acceptance-v2.json`，原始输出不改写；按新标签重算的记录在
`reports/task-judge-audit-20260926/reanalysis-v2.json`。原问法在四道指代不清题
均安全备用；两道等能力题也都备用。样本很小，且没有真实执行结果标签，不能据此
宣称选模质量已合格。

新增可选的 `choice-v2` 本地实验问法，在一次 `Choice` 中比较候选与「信息不足」，
保留原始概率并在轨迹中标出规则版本。实际 Laya 对修订后的四道指代不清题均安全
备用；两道等能力题也都备用。模拟能力差异题仍只算接口探针，直选在探索集命中
1／4、保留集 2／4，说明这套问法还不能替代结构化资格检查。记录保存在
`reports/task-judge-audit-20260926/choice-v2-option-development.json`、
`choice-v2-option-holdout.json` 和 `reanalysis-v2-choice-option.json`。

`choice-v2` 仅作显式实验选项，旧配置继续使用 `ordinal-v1`。它在候选能力卡缺失、
完全相同、媒体输入尚未验收或本地 tokenizer 检测到截断时使用指定备援，并在轨迹
说明原因；不会通过降低门槛强迫选择。当前用户模型池的长能力卡会触发 Laya 的
48-token 选项限制，所以此时切到实验选项也可能直接备用。短能力卡可完整输入的
本机测试约 94 input tokens、35 ms 暖机后推论，但结果仍不确定；该数字只描述本机
这一次调用，不表示质量或稳定时延。

下一轮真实质量验收应先冻结少量可独立判定结果的任务，分别运行池内两条固定路线，
得到每条路线在对应任务类型的实测证据；再将来源、适用范围和样本量写入能力卡。
保留题上同时运行 Task 和两条固定路线，按真实输出计算正确率、错误选模和备用率。
如果两条固定路线质量相同，只能证明 Task 可用与账本正确，不能据此宣称 Judge
做出了有收益的自主选择。真实调用前另列精确任务、调用数与 AFP 上限授权。

小样本协议已冻结在 `data/benchmarks/task-quality-pilot-v1.json`，执行入口为
`python -m experiments.run_task_quality_pilot`。从已有 Stage 冻结材料取两道校准题
（LRU 缺陷、存储方案事实核对）和两道保留题（slug 实现、检索方案比较）。校准题
分别跑两条固定路线；只有完整运行和独立检查的结果可压缩成短能力卡。保留题跑
固定 `deepseek-v4-flash`、固定 `deepseek-v4.1-flash` 和 `Task choice-v2`，共
10 次任务。代码按隐藏测试检查，研究按冻结引用和关键事实检查；不增加付费评审。

每次任务最多 5 次受管模型调用、5 分钟；每次调用输入最多 16000 tokens、输出
最多 2048 tokens；禁用委派和 HTTP 自动重试。根据冻结 Ark AFP 系数，整批理论
上限 **153.408 AFP／50 次调用**，本地 Judge API 费用为零。零调用预检记录在
`reports/task-judge-audit-20260926/task-quality-pilot-preflight-v2.json`；先前
3 次调用和 1024 输出 tokens 的 `v1` 预检已作废，保留作变更证据。独立的
`headless` DSH profile 已确认链接当前插件，Task 覆盖配置经 `--dump-config`
完成零调用组合检查；用户正在使用的 DSH profile 没有因此改动。

预检不等于付费授权。执行入口要求匹配的预检摘要和不低于上界的明确 AFP 授权，
且拒绝覆盖已有批次。校准任务未完整运行时不制造质量能力卡；认证、用量未知、
账本或证据写入异常会停止批次。实际质量报告必须同时展示 Task 的错误选模、
安全备用、有效自选和两条固定路线在保留题上的结果；四题只能支持探索性结论。

### Task 目标次序与 Judge 职责校正

用户明确指出 Task 选模应先满足任务，再追求成本较低，最后考虑时延。
现行 `choice-v2` 尚未实现完整的这个目标：它让 Laya 在候选中直选，
概率低于 0.8 时使用指定备援；没有在质量达标候选之间由 Python 比较费用和
时延。因此上述单题只能作为现行行为的验收证据，不能证明成本感知路由收益。

下一版应把判断和排序拆开：

1. Python 先按工具、媒体、上下文、数据域、权限和预算排除不可用路线；硬期限
   也属于准入约束。
2. Judge 对**每个合格候选**给出任务适合性和证据是否足够；未校准概率只作原始
   模型信号，不冒充任务成功率。质量不足或证据不全时使用明确备援。
3. Python 只在任务质量已达到冻结门槛的候选中比较**预计完整任务费用**，包含
   Judge、执行和必要工具／媒体路径，而非只比较每千 token 单价。AFP 和现金账本
   不直接相加；跨单位路线需要用户给出可比较的偏好或明确转换政策。
4. 在费用相近且时延资料可核对时，优先较快路线；如任务有硬期限，先在第 1 步
   筛掉不能满足期限的路线。缺少可靠时延样本时不伪造排序。

这套规则应写成版本化的 Python 选择合同和确定性测试，Judge 的提示只负责解释
任务与候选是否适合，不能把成本／时延最终取舍交给自由文字输出。现有 Laya
`Choice` 只返回单一首选与概率，无法证明其余候选也达到质量门槛；正式实行上述
排序前须扩展判别结果并在新的冻结题集验收。待执行的
`task-research-holdout-v2` 已标记暂停，避免沿旧目标继续消耗 AFP。

### Task 逐候选选择合同

Python 已将轻量 LLM Judge 的新请求改为逐一返回每个候选的 `score` 与
`missingInformation`，严格拒绝缺失、重复、伪造、越界或非有限分数。
本地 Laya 的逐候选问法沿用已有两问题批次，Python 使用全部候选的归一化结果；
`choice-v2` 只有首选概率，没有其他候选是否合格的证据，因此继续标为实验问法，
不据此做候选间费用排序。

判别前先排除本次缺少能力、数据域许可、上下文容量或一次调用预算的候选。
达到初始适合度门槛且没有关键信息不足的候选才参与排序。同一计费单位内按
**首次执行调用的保守费用上界**选择；上界相同且没有可靠可比时延资料时按
用户模型池顺序。没有合格候选或合格候选分属无法直接比较的计费单位时，
使用配置的备援路线，且仍须经过执行准入和预算检查。规则版本为
`task-quality-cost-v1`，路由轨迹保留各候选的原始信号、排除原因与费用上界。

首次调用上界无法预测任务总调用数与成功后的返工成本，**不等于完整任务预计费用**。
时延排序的可靠样本采集尚未接入，当前记录为 `unavailable`，不以模型名称
或未经核对的吞吐数字决定。逐候选分数也尚未完成真实质量校准，不能作为
任务成功率。本轮完成的是可解释、可检查的产品规则，不宣称已验证质量收益。
