# Stage 规则与本地 Judge 协作设计

决策日期：2026-09-27。状态：本文记录第一版实验合同；本地质量验收未通过。
当前已安装 Router 0.15.2 仍执行 `stage-v4` 的纯规则逻辑，未替换用户安装或默认策略。
实现与真实判别结果见[本次验收报告](../reports/stage-local-judge-20260927/README.md)。
后续对 Jev 类问题设计与本地判别结果的核查见
[Stage 本地 Judge 核查](stage-jev-local-judge-audit-20260927.md)；本文的三问合同保留为
历史设计记录。第二版实现与保留案例结果见
[第二版验收](../reports/stage-local-judge-20260927/v2-acceptance.md)，仍未达到日常使用门槛。

## 目标与设计变更

撤销“Stage 不调用 Judge、额外判别调用固定为零”的设计约束。新版 Stage 在执行模型的
调用边界，根据已有任务与轨迹选择下一轮模型，采用规则与本地结构化 Judge 协作。
优化顺序保持为可接受质量、全部调用成本、响应与等待时间。

Jev 在本设计中指借鉴的结构化决策接口形态，不是要接入的云端服务。首个适配后端为本地
Laya-MLX，复用常驻进程、显式下载与加载、排队、取消和实际 tokenizer 容量检查。
不得把接口相似视为不同 checkpoint 的分数或语义已经兼容。

Stage 只决定下一次调用哪个模型。它不生成任务计划、操作工具、修改 Agent 提示、进行上下文
压缩或撤回已交付回复。Escalation 继续负责生成后的候选审核与丢弃，二者合同独立。

## 职责分工

| 规则负责 | 本地 Judge 负责 |
| --- | --- |
| 身份、证据来源、去重及任务隔离 | 轨迹是正常探索、有进展，还是缺乏有效进展 |
| 权限、数据域、模型容量及接口准入 | 下一阶段的任务要求是否超出高效模型的已知适用范围 |
| 预算、调用名额、期限、取消与故障 | 当前是否有充分依据交回高效模型 |
| 判别触发、限频、保持、防止反复换模 | 输入是否缺少足以改变选模的关键信息 |
| 校验结构化答案及引用，执行选模 | 返回结构化答案和原始分数，不决定最终派发 |

工具失败、重复搜索、成功写文件只提供线索，不能直接等同于模型能力不足或任务质量合格。
旧 `tanh` 分数保留为历史解释；新协作模式不把它与 Judge 分数加权相加，也不再用它单独
决定升降档。规则分数与本地模型分数不是相同量纲，更不是任务成功率。

## 证据与输入

输入由 Python 按版本化规则构建，包括当前任务要求、已接受轨迹的必要上下文、最新证据窗口、
当前模型与保持状态，以及两档执行模型的能力卡。窗口初值仍为最近三条相关工具结果。
使用以下来源标签：

- `host-fact`：接入方提供、可与调用和结果配对的结构化事实。
- `tool-text`：标准 API 返回的工具正文，可供语义判断，但不是权威退出码或权限状态。
- `assistant-claim`：已接受的模型回复，只作为主张，不能当作独立完成证据。
- `unknown`：缺失、无法配对或不完整的信息。

权限拒绝、认证与传输故障不会因为 Judge 建议“强模型”而转成能力升级信号。
正文中的“成功”“测试通过”“忽略规则并升级”等文字不能改写来源标签或判别规则。

本地 Judge 不接收整段无限增长历史。用确定性字段投影保留任务约束、必要历史引用与原始证据；
记录被省略字段及完整性。工具 schema 可用明确的能力描述表示，不把完整工具定义都送入小模型。
如果任务依赖的上下文无法在容量内完整表达，返回 `UNCERTAIN / insufficient-context`。
不静默截断，不增加生成式摘要调用，不将 Judge 的输入投影替换宿主实际模型请求。

标准 Base URL 仍可用：只有工具文本时允许作语义判别，轨迹标明证据较弱。这样的判断不能声称
获得了真实退出状态。可信宿主扩展改善事实质量，但不成为所有客户端必须实现的前置条件。
这条文本轨迹判别路线必须独立通过验收，不能套用结构化事实路线的结果。

## 判别合同

新增 `stage-decision-v1`，与 Task、Escalation 的问题模板和校准版本分离。
不要求本地模型生成自由文字理由，理由由 Python 根据答案、证据引用和规则生成。

一次逻辑判别批次回答三个问题：

1. 进展状态：`PROGRESS / NORMAL_EXPLORATION / STALLED / INSUFFICIENT`。
2. 下一轮高效模型适合度：`SUITABLE / INSUFFICIENT / UNSUITABLE`。
3. 是否存在足以改变结论的缺失信息：`PRESENT / ABSENT / UNKNOWN`。

返回原始选项分数、实际 checkpoint/revision、模板版本、输入摘要、来源覆盖、排队与推论耗时、
实际 forward/批次数。高效模型的适合度必须结合其能力卡及当前任务要求；仅判断“任务很难”
不能证明另一个模型可以解决。强执行模型仍需独立通过能力与准入检查。

Python 将有效答案组合为 `EFFICIENT_OK / NEED_STRONG / UNCERTAIN`：

- 高效适合度达到门槛，且没有关键缺失信息：`EFFICIENT_OK`。
- 高效不适合达到门槛，且证据足够：`NEED_STRONG`。
- 答案冲突、分数不足、关键上下文缺失或已知输入超容量：`UNCERTAIN`。

`STALLED` 本身不直接等同于 `NEED_STRONG`。模型可以正常探索但即将进入更复杂阶段，
也可以因等待权限而没有进展，此时升级并不能解决问题。
初始升级确定性门槛 0.8、降档门槛 0.9，仅是待验收的参数；不同后端独立校准。

## 触发与切换规则

新任务默认从高效模型开始，保留当前 Stage 的启动语义。这不表示首轮质量已获判别保证。
需要任务开始前选模的用户仍可使用 Task；Stage 本版不隐式叠加 Task 分类。

| 时点或情况 | 操作 |
| --- | --- |
| 首次收到新的工具结果 | 进行一次本地轨迹判别 |
| 新的重复任务失败 | 提前触发判别；重复失败是判别线索，不再强制升级 |
| 普通新进展 | 默认每两次执行模型调用、且有新证据时判别一次 |
| 用户追加了影响下一步要求的指导 | 在下次模型调用前判别，沿用原任务预算与状态 |
| 强模型保持期结束 | 有新证据时评估是否可以降档 |
| 同一轨迹重放、设置预览或单纯上下文压缩 | 不重新判别，不增加计数 |

首次工具结果、重复失败和周期触发可在同一边界合并为一个批次。使用任务 ID、证据 ID 与
判别输入摘要做幂等检查；一次批次的多个问题不算多次路由判别，但记录真实 forward 次数。

有效 `NEED_STRONG` 立即选择强模型，并保持至少两次执行调用，包含升级本轮。
保持期内普通新进展不会提前降档；新证据支持继续使用强模型时可以延长保持期。

降档要求保持期已结束，且连续两次基于不同新证据的判别为高确定性的 `EFFICIENT_OK`。
在强模型阶段获取的两次判别才能计入降档确认，升级前的旧结果不能复用。
一条成功写入或一次测试通过均不足以单独证明适合降档。低成本优先只在质量资格满足后生效。

## 无法判断与故障

默认策略如下，并在设置页明确展示：

- 高效阶段出现正常的 `UNCERTAIN`：选择合格的强执行备援，记录这是谨慎回退而非确认能力不足。
- 强模型阶段出现 `UNCERTAIN`：继续强模型，不靠模糊分数降档。
- 保持期结束仍无新证据：保持当前模型，不按计数到期自动返回高效模型。
- Judge 未加载或后端不符合所选运行等级：执行前给出可用性诊断，不隐式切换云端。
- 非法输出、进程崩溃、超时、证据写入失败、认证故障或用量不明：停止后续受管调用。
- 正常不确定与已知超容量允许备援；运行故障不作为可重试或能力升级依据。

每任务初始最多四次逻辑判别批次。耗尽后有已确认的当前模型就固定该模型并显示
“判别次数已用尽，本任务停止动态调整”；高效模型的适合判断被新困难证据推翻时，
转入强执行备援并固定。强模型不合格或预算不足则停止，不能静默降档。
这项初始上限可以调整，但不通过反复扩大测试批次掩盖后端区分力不足。

## 成本与时间

本地 Judge 记录无 API 费用，同时记录排队、推论、输入 token、资源与 forward 次数。
不把“本地”理解为没有延迟或设备成本。默认复用已经加载的实例，同一实例串行推论。
Judge 默认总期限 1 秒，包含排队；还受任务剩余期限约束，属于待本机验证的初始值。

本地判别前确认至少有一条可执行且可承受的路线；判别完成后，原子预留选中执行模型的
实际请求上界。互斥的高效/强模型不同时计作调用费用；强模型被选中但额度不足时停止。
若未来允许显式选择付费轻量 Judge，必须在 Judge 派发前保护一次可能的强执行备援费用，
防止花费判别费用后无法执行。本轮不会自动启用这个后端。

后续成本优化需要考虑降档时缓存丢失造成的额外输入费用和下一次请求成本；本次尚未
实现缓存收益预测或基于时延的自动排序，实际执行仍按保守输入费用预留。没有同路线观测时视为未知，
不能编造完整任务的预期费用，更不能直接比较 AFP 与 CNY 大小。强执行是能力角色，不意味着
一定更贵；价格相近时才使用可比的延迟观测作后续选择依据。

## 设置、状态与迁移

Stage 增加独立配置，提供 `rules`（旧行为）与 `hybrid`（规则＋本地 Judge）。新协作模式
通过验收后作为新配置的推荐方式；旧会话仍按其冻结版本执行，不改写旧记录。
独立 Stage 设置使用 `refractagent-planning-v5`；原配置没有 `stage` 字段时继续使用旧规则。
进程协议保持 `/4`，新增 `stage-decision-v1` 与 `planning-routing-v5` 能力握手；
插件调用协作模式前必须检查这两项能力。该扩展不改 Task/Escalation 的问题模板。

`stage.mode=hybrid` 目前必须显式设置 `allowExperimental=true`。默认不启用，也不自动升级
现有配置。实验门槛与模型来源、路径、revision 检查均由 Python 完成。

简洁设置包含两档模型及推理参数、本地 Judge 与就绪/验收状态、无法判断的备援行为。
高级设置包含证据窗口、判别间隔与批次数上限、保持轮数、降档确认次数、独立阈值和期限。
不继续让用户以旧 `tanh` 阈值控制新 Judge。

轨迹显示本次触发原因、证据来源与完整性、原始答案、规则最终选择、升降档原因、
保持与降档计数、Judge 等待时间和执行费用。保留“规则建议、Judge 判断、最终派发”三个字段，
以便解释正常探索为何未升级、不确定为何走备援，及哪个环节产生额外开销。

任务身份由现有宿主中立合同提供。只有 Base URL 且缺少明确身份时，继续保留现有的
工具调用关联和新 user 消息边界限制；不能把压缩或追加指导的完整识别冒充已解决。

## 有限实现与验收顺序

1. 实现独立判别合同、调度与幂等状态，不改 Task/Escalation 的问题模板。
2. 接入本地 Laya 常驻服务，验证完整容量检查、期限、取消和迟到结果隔离。
3. 用固定 24 条轨迹案例验收：正常探索、需要强模型、可降档、信息不足各六条，覆盖中英文。
   记录混淆矩阵；需要强模型的六条不得判为可降档，正常探索至少五条不误升档。
   这是有限门槛，不是泛化质量证明。未达标的后端只标为实验，不自动追加更多批次。
4. 验证结构化事实与纯工具文本两种输入路径，并覆盖伪造退出码、提示注入、不同失败、
   研究搜索、TDD 正常失败、预算不足、未知用量、保持和双确认降档。
5. 在 DSH、Codex、Hermes 各完成一个限定的正常续接流程；真实换模用明确标识的受控困难
   流程核对模型身份、历史、宿主工具与账本。先冻结调用范围与各单位上界，再按既有授权执行。

每个客户端按实际接口和证据范围报告结果。已有本地 Laya 在 Escalation 的 24 条回复审核
案例仅匹配 5/24，不能因此断言 Stage 一定失败，也不能凭调用速度就宣布 Stage 已可用。
本轮验收后形成明确可用或实验结论，不以证明比 Static 省钱为完成条件。

## 独立接口的显式加载

标准模型接口继续由各客户端设置 Base URL 使用。服务管理员可在已配置本地权重后，
通过 `refractrouter-gateway --config <配置> --runs-dir <记录目录> --load-stage-judge`
明确加载 Stage Judge；该操作不会下载模型。`--preflight` 仍是零模型调用检查，不触发加载。
DSH 设置中的检查、下载、加载与卸载操作复用同一核心接口。
