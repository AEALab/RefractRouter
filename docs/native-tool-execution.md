# DAG 节点的宿主工具执行

## 问题与修复边界

旧版本把 DSH 技能目录放入节点上下文，但只支持文本模型响应。模型可能输出
`<|FunctionCallBegin|>` 等文本；既没有原生工具参数，也没有宿主执行与结果回传。
这不是输出额度或安装审批导致的工具调用失败。

核心 0.6.0 与插件 0.17.0 为执行节点添加原生工具循环，保留 Python 选模和 DAG。
规划器和最终评审仍只调用模型。普通独立 Python 文本入口没有工具宿主时保持原行为。

## 职责与协议

- DSH 本次请求的 `tools` 是能力边界。插件不从全局注册表扩大权限或可见工具范围。
- Python 收到原生 `tool_calls` 后先确认用量、结算账本，再发出 `refractrouter-tools/v1`
  请求。正文里的调用标记不解析为命令，直接以明确错误停止该节点。
- TypeScript 捕获真实 `agents.requireInitiator()` 与当前 step，调用 `tools.execute`。
  不伪造 Agent、父执行令牌或审批结果。工具串行执行，模型节点仍遵循 DAG 并发配置。
- 每个工具调用使用独立宿主 callId，在插件 `refractagent/tool-call`、`refractagent/tool-result` 日志中配对。
  DSH 原生 `tool/result` 必须带 surface 标记，会加入外层模型历史，不能用作节点内部日志。
  节点内部工具消息只送回该节点，不向外层模型 surface 插入孤立的 tool result。
- 技能的 `additionalContexts` 与工具结果一起送回节点。节点完成后才释放下游。
  原生工具返回 `concludesTurn` 时停止剩余工具、DAG 和评审，保留已完成结果及中止状态。
- Chat Completions、Responses、DSH 模型桥分别转换原生工具历史；Responses 保留推理
  replay 项，DSH 保留 provider replayState。底层 HTTP 仍为零重试。
- 同一个 stdio 通道串行关联模型与工具请求；DAG 进度写入共享行锁，避免并发字节交错。

## 预算、失败与限制

每个节点最多 16 次工具续调、每任务最多 64 次工具执行；达到边界明确失败，不无限循环。
每轮重新计算消息与工具 schema 的输入预留，沿用用户生产预算、上下文及输出配置。
预算不足、未知用量、截断响应、取消或桥接中断不会继续执行工具。
执行过工具的节点不自动回退选模或动态拆分重跑；这避免副作用重复，但可能需要用户在
确认工具实际结果后重新发起任务。普通无工具节点的既有回退策略不变。

宿主工具可以自己访问网络、文件或调用子 Agent。它们的权限和内部费用由 DSH／相应工具
管理，不计入 Python 模型调用账本；不能把 Router 的模型预算解释为这些外部操作的总费用。
工具结果以文本与内容引用提供给节点；不新增图片、音视频生成模型入口。可用工具按本次
宿主请求冻结，运行中新增注册的工具要到下一次宿主请求才可见。

## 验证与交付

无网络测试使用模拟技能、模拟天气工具和模型响应，覆盖技能加载、工具证据回传、下游
解锁、每轮计费、schema 预留、拒绝、取消、截断、重复调用、轮次边界以及 Responses
和 DSH replay。原 DAG／插件配置共同注册与历史回放测试继续保留。

模拟测试不能证明真实天气查询或每个供应商模型的工具调用质量。安装后核对核心与插件版本、
服务加载、DAG 与设置页；不以模拟天气结果宣称真实外部查询已验证。

另提供已安装 DSH 运行时的离线冒烟脚本，直接验证原生工具执行、技能附加上下文、
审批拒绝及拒绝后工具函数未被调用；不会访问真实服务或提交模型请求：

```sh
npm run --prefix validation/dsh/plugin build
node --experimental-strip-types validation/dsh/plugin/scripts/check-native-tools.ts "$DSH_NODE_MODULES"
```

`DSH_NODE_MODULES` 指向已安装 DSH 的 `node_modules` 目录，脚本核对的宿主版本为
`0.1.1-rc.2`。测试中的审批服务与 Agent 为内存夹具，原生 `ToolRuntime` 为宿主实际实现；
它证明执行管线兼容性，不证明浏览器的审批提示已完成真人端到端验收。

## 0.6.1：区分已知输入与上游最大容量

自动规划曾把「完整上下文 + 每个父节点最大输出 token 数 × 8」作为已发生的输入，
超过默认 131,072 就直接拒绝计划。长会话中，这可能在尚未执行首个节点时触发
`automatic-plan-input-capacity-exceeded`，并不表示模型已收到超限请求。

0.6.1 保留最坏情况估计供诊断，但把自动契约预算限定在配置上限之内；上游输出到达后，
派发前按实际完整请求再检查。已知材料本身超限仍立即失败；不截断材料、不修改显式契约，
也不打开用户的上下文放宽开关。自动重拆继承同一上限。

工具 schema 与工具执行说明纳入初始规划、准入和实际节点输入的同一计数方式，
防止规划估计与执行阶段使用不同口径。新增回归覆盖长上下文短上游、真实上游超限、
已知材料超限、工具说明容量及自定义上限；保存的失败计划以模拟模型无网络回放通过。

## 执行节点输出容量

核心 0.6.2 起，应用执行节点及工具续调使用模型容量，不再受部署级小输出额度与历史
Chat Completions 8192 上限夹断。Ark 使用仓库模型目录中的容量；其他供应商遵循用户
声明的 maxOutputTokens。思考设置保持不变，输入和工具定义占用的上下文会在每次预留时扣除。

总预算及每轮记账保持生效；最大输出容量不是免费额度，保守预留超过剩余预算时会在派发前
拒绝，不能保证所有任务在原预算内完成。历史实验 ModelSpec 和评审输出限制保持原行为。
本次使用模拟传输验证超过 8192 的额度到达实际请求参数，未新增付费模型调用。

## 应用请求超时

核心 0.6.3 起，应用 HTTP 客户端不再附加默认 120 秒限制，执行节点与工具续调使用
任务剩余时间；规划器继续使用已有的无本地超时路径。任务总期限及历史客户端默认值
不变。错误记录保留白名单中的超时毫秒数和传输阶段，不公开供应商正文或凭据。
