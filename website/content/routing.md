# 两种路由怎么选

两个入口共享已适配的模型目录、价格依据和安全准入，但采用不同执行结构。

## 入口比较

| 项目 | 规划路由 | 自动路由 |
| --- | --- | --- |
| 关注点 | 每次模型调用使用谁、是否审核或接管 | 整任务 Direct 还是任务 DAG、节点如何分配 |
| 任务拆分 | 不创建 DAG | 必要时由规划模型生成 DAG |
| 执行循环 | 接入方 Agent 的原生循环 | 独立任务运行时，工具仍由宿主执行 |
| 用户设置 | 六种策略各自的执行器、Judge 和参数 | 执行模型池、规划、拆分、最终审核与预算 |
| DSH 主要展示 | 路由轨迹中的调用流程 | 任务 DAG 和自动路由记录 |
| 标准 Base URL | 六个 `refract/*` 虚拟模型 | 不通过标准模型 API 隐式进入 DAG |
| 当前定位 | 文本与原生工具的模型路由 | DAG 拆分与收益探索的独立入口 |

## 建议的选择顺序

日常任务先从规划 Static 开始。固定模型可用后，再根据需要选择 Stage、Task、Advisor、
Escalation 或 Composite。需要验证独立子问题与并行调用时，单独选择自动路由。

自动路由选择 Direct 时，它仍属于自动路由运行记录；不是自动变成某个规划策略。
Advisor 的最终回复 Gate 与自动路由的最终 Judge 也不是同一个策略配置。

## 三类判断不要混淆

1. **能否拆分**：有没有独立子问题、依赖是否允许分开处理。
2. **是否选 DAG**：准入、质量依据、规划与汇总开销、费用及时间预测是否支持它。
3. **候选能否交付**：实际输出、工具证据和审核结果是否满足任务合同。

Jev 可以为其中适合有限回答的问题提供信号，Python 执行最终规则。
“可以拆分”不等于“DAG 更便宜”，审核通过也不反向证明当初选路最优。

## 共同边界

Router 不承担技能组织、智能体驾驭工程、工具权限、上下文压缩或子 Agent 任务管理。
DSH 与 Codex 的接入合同不同，不能因为模型 API 返回成功就宣称其全部功能兼容。
本轮产品范围以 DSH 与 Codex CLI 为主；其他客户端的历史实验不扩大当前承诺。
