架构：Python 核心与 DSH 插件 ​

RefractRouter 是单仓库、分层职责的结构：Python 核心拥有所有路由决策，TypeScript 插件只是宿主适配层。理解这条边界，是理解项目所有行为的第一步。

为什么要这样分 ​

模型路由的价值取决于决策的一致性和账目的可信度。如果选模规则同时存在于 Python 和 TypeScript，两边的行为偏差会直接导致实际调用与记录不符。因此项目约定：

  • 路由、评分、预算记账、Go/No-go 判定只实现一次，全部在 Python。
  • 插件只做三件事：把宿主请求转成核心协议、把核心签发的调用交给宿主模型服务、 把结果和轨迹展示给用户。
  • 核心不绑定 DSH：标准模型网关走 HTTP，Codex CLI 不需要 DSH 也能使用六策略。

插件位于 validation/dsh/plugin/ 是历史原因；它现在是产品化入口之一，不是验证工具。 包名保留 dsh-refractrouter-validation 仅为兼容已安装版本。

一次规划路由调用的旅程 ​

以 DSH 中的一次 Stage 调用为例，数据这样流动：

  1. DSH 原生循环准备发起模型请求，插件拦截这个请求，通过本机子进程发给 Python 核心。
  2. 核心按冻结的任务状态和策略规则选出目标模型，原子预留预算后签发调用指令。
  3. 插件把调用转给 DSH 的模型服务，模型流式返回；工具调用原样交回 DSH 执行。
  4. DSH 的工具结果作为结构化证据随下一轮请求回到核心，核心据此决定下一轮用哪个模型。
  5. 每次调用的费用、判别、接受或丢弃都写入本机证据文件，界面读取这些记录展示轨迹。

这个循环里没有任何一步需要核心理解 DSH 的工具语义；核心只消费证据状态 （completed / failed / denied / unconfirmed），这正是它能同时服务 Codex 的原因。

一次自动路由任务的旅程 ​

自动路由由核心独立调度（仍属研究入口）。任务整体进入核心后，先过零调用准入， 再判断是否值得为拆分付费；只有结构信号支持时才调用规划模型，然后比较 Direct 与 DAG 的完整成本。详见自动路由的流程图。

语言边界的硬规则 ​

  • TypeScript 中不得出现路由、评分、预算或 Go/No-go 判定逻辑；插件可以在调用 Python 前检查部署级限制（比如宿主预算上限），但不能替核心做决策。
  • 编译生成的 dist/ 是运行产物，不手写、不提交。
  • 新增实现语言或跨层复制业务逻辑，须先在架构 Issue 或 ADR 中提案并获维护者批准。

这些规则不是风格偏好，而是防止两个权威实现漂移的机制。历史事故与恢复核对记录在 仓库的 DAG 恢复核对文档中。
